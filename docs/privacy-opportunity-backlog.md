# Privacy Opportunity Backlog

These are candidates, not promises. Prioritize by user impact, feasibility, evidence quality, and the risk of misleading the user. The sourced review dated 23 October 2026 lives in [privacy feature research](research-notes/privacy-feature-research-2026-10-23.md).

## Buildable with local processing or public APIs

### Photo and document metadata inspector / scrubber
People often share GPS coordinates, device details, timestamps, author names, and editing history unintentionally. Inspect files locally, preview fields to remove, and write a sanitized copy rather than silently altering the original. Validate behavior per file format.

### DNS protection status and leak diagnostics
Users may believe a VPN or DNS blocker is active when a configuration change, IPv6 path, captive portal, or encrypted-DNS setting bypasses expectations. Show tunnel/resolver state, test configured paths, log rule hits and failures, and explain what cannot be observed. A diagnostic cannot prove every service uses the expected path.

### Permission drift and unused access review
Compare available OS permission state over time where public APIs permit it; create reminders and links to native settings. Do not pretend an ordinary app can universally revoke other apps' permissions.

### Offline breach exposure lookup
Offer optional local lookup against a documented downloaded dataset, without submitting the raw email to a third party. State coverage and update date; datasets are incomplete and can be stale.

### App privacy change alerts
Compare user-selected APK versions locally, show exact differences, cite signature database revisions, and distinguish declared capability from observed behavior. Obfuscation and dynamic loading limit static analysis.

### Smart-device inventory
Use opt-in local discovery and user-approved scans. Label vendor/model attribution as uncertain unless verified. Network isolation and randomized MAC addresses limit attribution; never scan networks without permission.

### Privacy-preserving log export
Provide a local preview with field-by-field redaction, export minimization, retention controls, and no automatic upload. Test redaction deterministically and warn that rare combinations can still identify a user.

## Research before implementation

### Stalkerware and coercive-monitoring safety signals
Investigate documented patterns such as unexpected device-admin privileges, accessibility access, persistence, or unknown management profiles where the OS exposes them. Signals are not proof. Safety guidance must avoid actions that could unexpectedly alert an abuser.

### Browser fingerprinting education
Explain canvas, font, WebGL, and related fingerprinting surfaces. Direct users to browser-level protections that exist; do not promise randomization from a companion app that cannot control another browser's rendering APIs.

### Ad identifier and tracking-setting reminders
Where an OS exposes a relevant identifier or setting, explain it and link to native controls. Resetting an advertising ID does not erase historical profiles or prevent all cross-app tracking.

### IoT outbound-traffic baseline
If router logs or a user-controlled DNS resolver provide data, identify new destinations and changes. A phone VPN alone cannot reliably observe traffic generated by every other device on the LAN.

### Data broker opt-out workflow
Identify brokers, explain opt-out routes, draft requests, and track submission evidence. Automate only verified forms and current legal requirements. Never imply that a request guarantees removal from resellers or copies.

## Additional evidence-backed candidates

### Protected local settings and export lifecycle
Protect persisted sensitive settings with platform-native key storage, versioned migration, crash-safe writes, and clear unrecoverable-key handling. This is distinct from the passphrase-encrypted export format; it does not provide sync.

### VPN preflight and observed service state
Explain VPN replacement behavior and data handling before consent. Report actual service lifecycle and tested route diagnostics. Do not imply a successful tunnel means IPv6, encrypted DNS, or every app path is covered.

### App-update privacy diff
Compare selected APK versions locally for manifest permissions, exported components, SDK signature matches, and embedded endpoint candidates. Record the APK hash and signature database version; never present static indicators as observed runtime behavior.

### Minimal, redacted audit export
Let users choose the date range and event categories, preview redactions, and exclude raw DNS names, packet payloads, internal paths, and identifiers by default.

### Offline breach-exposure lookup
Use a sourced, appropriately licensed local dataset with an explicit refresh date and coverage limitations. Do not send a raw email address to a third-party lookup service by default.

### Data-broker request assistant
Maintain verified opt-out links and source dates, draft user-reviewed requests, and store submission evidence separately from a confirmed company response. Do not promise removal from downstream copies.


### Authenticated encrypted DNS upstream
The current upstream DNS path uses plaintext UDP/TCP. Research a strict DNS-over-TLS or DNS-over-HTTPS transport with explicit resolver hostname verification, no silent plaintext fallback, and tests for certificate failures. A secure channel still exposes queries to the chosen resolver and does not cover traffic that bypasses the VPN.

### Backup and restore privacy audit
Verify backup flags and XML rules in CI, then test cloud restore and device-to-device transfer on supported Android versions/OEMs. The manifest's explicit backup posture is evidence of configuration, not proof that every vendor transfer path behaves identically.

## Prioritization rule

Prefer features that provide a useful, verifiable result without root, jailbreak, hidden collection, or a mandatory server. Do not build an impressive dashboard before the underlying evidence and enforcement are real.
