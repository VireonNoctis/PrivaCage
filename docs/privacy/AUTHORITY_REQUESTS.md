# Authority and Legal-Request Policy

**Version:** 0.1-draft  
**Prepared:** 3 November 2026

## 1. Our default position

PrivaCage does not voluntarily sell, share, broker or disclose user data to law-enforcement, intelligence, immigration, regulatory, military or other government authorities. It does not run an authority-access portal, backdoor, user-account search system or routine authority data feed.

The project does not maintain a central PrivaCage user-account database. The Android client does not upload local privacy reports or local app/DNS inventories to the project by default. The configured relay is not a central PrivaCage account service and the repository relay defaults to loopback.

This is a policy against voluntary disclosure, not a promise to disobey a valid legal obligation.

## 2. What the project itself may have

The answer depends on the exact deployment. The repository alone does not create a centrally operated service.

### 2.1 Default local Android use

For local-only use, the project maintainer does not receive:
- local DNS history or configured block rules;
- the permission-audit baseline or launcher-visible app inventory;
- app-policy review queue contents;
- rights-request tracker metadata;
- local APK inspection results or media metadata findings;
- AI API tokens;
- sync private keys or readable sync profile payloads; or
- local audit checkpoint files.

This remains true only while the user keeps that data on the device and does not voluntarily send/export it to another person or service.

### 2.2 Public web deployment, if one is operated

The Rust web API currently defaults to loopback and serves the embedded tracker catalogue. It is not a user-account service or connected-device telemetry collector.

If the project owner or another operator publishes the website/API publicly, ordinary hosting infrastructure or a reverse proxy may log basic connection metadata, depending on its configuration:
- source IP address;
- connection/request timestamp;
- requested URL path and method;
- user-agent and protocol metadata;
- request/response size or status code; and
- security or abuse-prevention records generated by the host.

The repository's catalogue API does not need a user's private DNS history, app inventory, rights requests, AI token or device sync keys to serve the public catalogue. The actual host operator must disclose its real logging and retention configuration.

### 2.3 Encrypted sync relay

If an operator hosts a relay and receives a valid legal request, data that may be available in its relay database includes:
- space identifiers and message identifiers;
- public device cards and public device fingerprints;
- timestamps, sequence/cursor information and access patterns;
- packet payload lengths;
- opaque encrypted packet bytes; and
- a stored hash of a relay capability token.

The relay does not store the plaintext capability token and does not hold the recipient private keys needed to decrypt packet contents. It can provide packet ciphertext and routing metadata if legally required and if those records still exist. It cannot turn those ciphertext bytes into readable profile contents using the relay database alone.

The hosting provider or reverse proxy may separately hold IP/request logs. Those logs are controlled by the relevant infrastructure operator, not necessarily by the PrivaCage project. Relay packet records expire after seven days under the current code; proxy logs have no project-wide retention period because they are not configured by this repository.

## 2.4 The limited operational information that may be disclosed if lawfully required

Where a project operator actually operates a public endpoint and holds the relevant records, the ordinary categories that could be produced are limited to:

- **Basic connection records:** source IP address as seen by that endpoint, request time, HTTP method/path, user-agent/protocol, response status, and approximate request/response size, but only if the hosting stack actually logs and retains those fields.
- **Relay routing records:** space ID, message ID, cursor/sequence and timestamps, public device-card/fingerprint details, packet length, access patterns, and an opaque encrypted packet payload that the relay database stores.
- **Security/abuse records:** a capability-token hash and narrowly scoped administrative/security event records, if the relevant deployment actually records them.

The project does not hold a PrivaCage user account list, local DNS history, device app inventory, rights-request tracker, AI token, device private sync key or plaintext sync profile from the default local-only Android installation. The relay's stored packet bytes are encrypted for recipients; a relay operator cannot make them readable using the relay database alone.

This is a description of the intended repository implementation, not a guarantee about a separately configured reverse proxy, cloud host, DNS resolver, AI provider or another operator. Those providers may possess additional records and must be assessed under their own notices and legal obligations.

### 2.5 Information submitted to third parties by the user

If the user confirms an AI request, the selected AI provider receives the text and API authentication information needed to process it. If the user uses a DNS resolver, that resolver receives DNS questions. If the user opens an external web page, that destination receives the ordinary connection metadata. Those providers may be subject to their own legal requests.

PrivaCage cannot promise what a separate provider will disclose under its own valid legal process. The user should review that provider's current policy and legal-disclosure transparency before sending sensitive information.

## 3. What we will do if a legal request is received

Where the project operator receives a request that purports to require disclosure, the policy is to:

1. confirm which legal entity/operator received it and preserve only records that are lawfully required to be preserved;
2. verify the identity of the issuing body, jurisdiction, legal authority, scope and validity of the demand;
3. seek qualified legal review where appropriate;
4. challenge, narrow or seek clarification of an invalid, overbroad or legally contestable request where legally available;
5. disclose only the minimum information that is lawfully required and actually held or controlled by the recipient operator;
6. not create data that the project does not possess, decrypt ciphertext without a key it does not hold, or provide a private key/backdoor that does not exist; and
7. notify affected users when legally permitted and safe to do so. A secrecy direction, statutory prohibition, or genuine risk to a person may prevent or delay notification.

The project will not promise that every request can be challenged, that every notice can be sent, or that a legal demand can never compel disclosure.

## 4. Legal context

For processing subject to the GDPR, Article 6(1)(c) recognises processing necessary to comply with a legal obligation to which the controller is subject. Article 23 permits certain restrictions only through qualifying Union or Member State legislative measures and subject to necessity, proportionality and safeguards. Article 48 addresses third-country judgments and administrative decisions seeking disclosure, in conjunction with the GDPR's international-transfer rules.

Irish Data Protection Act 2018, section 41, addresses certain necessary and proportionate further processing for national security, public security and criminal-offence purposes. It is not a blanket instruction that every private app developer must disclose every item to an authority.

Section 41 of the Irish Data Protection Act 2018 (revised to 16 July 2026) concerns necessary and proportionate further processing for specified national-security, public-security and criminal-offence purposes; it is not a blanket rule that requires a private app developer to disclose any information requested. GDPR Article 48 and the EDPB's final Guidelines 02/2024 (version 2.1, adopted 4 June 2025) address requests from third-country authorities and the need to assess an applicable international agreement and GDPR transfer rules.

The actual legal result depends on the authority, legal instrument, jurisdiction, controller/processor role, data location and facts of the request. This policy is not legal advice.

## 5. Our limits

- We cannot protect data that the user has already sent to an AI provider, resolver, browser, store, relay operator or another recipient.
- We cannot control a user's device being seized or accessed while unlocked.
- We cannot promise that Android, an OEM, a carrier, a network operator or a hosting provider has no logs.
- We cannot provide plaintext sync data from ciphertext stored by the relay if the relevant private keys are not held by that operator.
- We cannot promise that a third party will follow the same no-telemetry or legal-request policy.

## 6. Public reporting

The project should publish a transparency report if it later operates a central public service and receives meaningful legal requests. Do not publish details that would identify a user or breach a legal restriction. Until a central service exists, do not fabricate request counts or claim that zero requests were received.
