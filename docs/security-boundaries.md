# Security boundaries and verification status

This document is a claim boundary for PrivaCage. A capability is not treated as implemented just because an API, design sketch, or roadmap item exists.

## Implemented in the current branch

| Area | Evidence-backed claim | Boundary |
|---|---|---|
| Sync relay per-device access | Admin-authenticated APIs provision distinct capability hashes and validated public cards per full device fingerprint, expose a token-free member roster, activate per-device authorization, and selectively revoke or replace a member token. Android now offers an in-app lost-device revocation action that prompts for the administrator token per operation, verifies member mode and target membership before DELETE, does not persist the admin token, and records success/failure in local lifecycle history. Member-mode requests require Ed25519 proof of possession over method, exact path/query, timestamp, nonce, and request-body digest; the relay enforces a 120-second clock window and durable nonce replay rejection. | The operator controls enrollment, so this is not an owner-signed roster or account service. Selective revocation fails closed if legacy shared-capability mode is still active; rotate that shared capability or activate member mode first. Compromise of both a member bearer token and its identity private key defeats device binding. |
| PCAGE01 encrypted profile envelope | Kotlin/JVM and Rust can decrypt the same checked-in known-answer vector. Production encryption uses Argon2id v1.3 and AES-256-GCM with fresh OS-generated salt and nonce. | The vector checks interoperability for one fixture; it is not a cryptographic audit. |
| Rust profile payload | The Rust API validates JSON shape, version, numeric IPv4 resolver, normalized domains, duplicates, and size limits before returning a typed profile. | Calling code must still validate before applying imported settings. |
| Tracker signature catalog | The canonical JSON schema and basic evidence URL structure are checked by CI. The Android loader enforces exact field sets and requires `schema_version` to be the integer value `1`, rejecting coercible values such as `1.0` or `"1"`. CI also rejects evidence review dates older than 180 days, which forces re-review but does not prove source truth or availability. New catalog records include source URLs and evidence descriptions. | Schema validation does not prove that a source is accurate, current, or independent. The current dataset has fifteen curated records and remains a small starter set. A review-report script calculates current, due-soon, overdue, and invalid-future-date states; CI still gates evidence dates at 180 days. |
| Local signed tracker release store | The Rust tracker-intelligence tooling signs release manifest v2 metadata (catalog digest, sequential version, predecessor-manifest digest, creation/expiry dates, and signer key) using Ed25519. Immutable releases are linked in sequence; the current pointer is signed and records the chain head separately from an explicitly selected rollback target. Verification checks catalog and pointer signatures, history continuity, current-release expiry, and optional externally supplied sequence/revision floors. | This is local release tooling, not a remote updater or full TUF client. Strict rollback protection requires the caller to persist the highest accepted release sequence and pointer revision outside the store; replay of a whole older store snapshot cannot be detected from files inside that snapshot alone. The Android app still consumes the catalog bundled inside the APK. Signer-key rotation is unsupported; pin the public key out of band. |
| Android backup declaration | CI verifies that the source manifest explicitly sets `android:allowBackup="false"`. | This is a static configuration check, not proof of behavior across every Android release, OEM migration path, or device-to-device transfer. Device tests are still required. |
| APK static audit | The user-selected APK is parsed locally for requested permissions, version/target-SDK metadata, APK SHA-256, current signing-certificate SHA-256 fingerprints, exported components, and bounded DEX literal-marker searches. Android uses Google's `apksig` verifier to check APK signature integrity across supported signing schemes; malformed/invalid and verification-error states are reported separately. The temporary copy is deleted after inspection. | A valid signature proves integrity relative to the included signing certificate, not publisher identity or safety. The Rust CLI still only extracts v2/v3 certificate fingerprints and does not verify signatures. Static declarations and strings are not proof of runtime behavior; coverage caps, obfuscation, native code, and unsupported archive formats can cause missed indicators. |
| Rust metadata inspector/scrubber | The local Rust core recognizes JPEG APP1/APP13/COM segments, PNG eXIf/text/time/physical-resolution chunks, and WebP EXIF/XMP chunks. The Android adapter previews findings from a selected file, scrubs to a separate temporary copy, re-parses the result, and requires a zero-recognized-metadata verification before offering a save. | It does not decode pixels or remove metadata from unknown JPEG APP markers, unknown PNG/WebP extensions, or preserved color profiles. It does not scrub pixel-visible identifiers and is not a universal anonymizer. Supported formats are JPEG, PNG, and WebP; file processing is capped at 100 MiB and remains local. |
| Signed audit checkpoint | The Android app hashes each selected/redacted event into a deterministic SHA-256 chain, then signs the exact export payload digest, chain head, record count, creation time and public-key fingerprint with ECDSA P-256 using a private key held by Android Keystore. The verifier checks the signature, payload digest, event links and whether the public key matches the key currently in this installation. | A signature cannot prove that unrecorded events never occurred or that the device clock is correct. The embedded key does not identify a person; trust it only after independently confirming its fingerprint. Android Keystore hardware backing varies by device. Checkpoint JSON is plaintext and may contain hostnames/socket-owner labels if explicitly included. |
| Portable signed audit checkpoint verification | The Rust `pcage-audit` CLI/library verifies the embedded payload digest, P-256 ECDSA signature, exact event chain, count/counters, supported schema, size limits and redaction claims. The fixed checked-in interoperability vector is independent of the Rust signing helper. Android checkpoint parsing also applies bounds and validates the intended P-256 curve. | The public key is embedded and self-asserted; a valid signature does not identify a person or trusted device. Independently confirm the fingerprint. The portable verifier cannot prove event completeness or clock accuracy, and it does not have an IANA timezone database to independently recalculate every local-date conversion. No Rust/Android build or CI result is claimed until the workflow actually runs. |
| Android DNS policy core | The local core evaluates configured domain rules and handles the documented IPv4 UDP DNS path with upstream UDP/TCP fallback for truncated responses. Optional DNS-over-TLS uses certificate hostname verification and fails closed instead of falling back to plaintext. A local device snapshot reports exposed location, Wi-Fi, Private DNS, and active-default-network VPN settings; a separate local audit reports declared dangerous permissions and grant flags for launcher-visible apps. An opt-in, bounded local DNS event history records hostname, decision, timestamp, and best-effort socket-owner information. | Counters describe core outcomes, not successful delivery to apps. The VPN adapter is early implementation and has not been release-validated on a representative device matrix. Package visibility omits some packages, and neither audit can identify all privileged OS/OEM collection. |

| Windows read-only baseline auditor | `windows/pcage-audit/` runs on Windows 10/11 and reads Domain/Private/Public firewall profile configuration from the active policy store, plus selected machine-level Windows diagnostic-data and App Privacy policy values. It produces source-linked JSON/text and distinguishes unknown reads from absent policy values. The collector performs no network requests or writes. | This is a limited point-in-time configuration audit, not a calculation of effective user/MDM policy, per-app permission grants, live traffic monitoring, process attribution, firewall rule management, or proof that data was sent. Values may be interpreted differently across Windows editions and versions. |
## Explicitly not implemented or not established

- **E2EE sync remains an early Android client + protocol + relay integration, not a complete sync product.** The Rust core provides per-device Ed25519/X25519 identities, signed recipient-encrypted packets, replay protection, peer-key rotation, dual-signed owner-key rotation, recovery, and an owner-signed device roster. Owner rotation binds the current space and exact roster revision; receiving devices verify signatures from both old and next owner keys, independently confirm the new full fingerprint, and require the signed next roster before replacing the local pin. Android publishes the replacement owner-signed roster when relay authorization allows; a relay member credential may still need separate administrator provisioning. Android verifies monotonic roster revisions and gates peer send/receive trust against the pinned roster. First owner trust and every owner-key replacement still require out-of-band fingerprint confirmation. The relay can deny service and still sees routing metadata. There is no iOS/Windows client, background push, conflict resolution, independent cryptographic audit, or representative physical-device lifecycle validation.
- **DNS encryption is optional and scoped.** When explicitly enabled, the configured upstream uses DNS-over-TLS with certificate hostname verification and no plaintext fallback. When disabled, upstream DNS uses UDP/TCP. The feature covers only the supported DNS path; it does not encrypt arbitrary device traffic or hide queries from the chosen resolver.
- **DNS counters are aggregate only; optional event history is separate.** Aggregate counters retain no queried hostnames. A user can explicitly enable a bounded local history that stores hostnames, decisions, timestamps, and best-effort socket-owner labels on-device; recording is off by default and the user can clear it. Socket-owner lookup may be unavailable or identify Android's system resolver, not the originating app. No history is uploaded by this feature.
- **No universal traffic visibility.** The current Android path handles IPv4 UDP DNS only. It does not prove coverage of IPv6, DoH, DoT, DoQ, direct-to-IP traffic, apps using their own encrypted resolver, or traffic from other LAN devices.
- **No full-device VPN lockdown yet.** The current VPN routes only the configured virtual DNS endpoint, not all device traffic. Do not enable Android's “Block connections without VPN” with PrivaCage as the selected VPN; ordinary app traffic may be blocked. The app links to VPN settings only with an explicit warning.
- **No universal app attribution.** The event history attempts Android 10+ UDP socket-owner lookup when available, but this is not reliable proof of the app that initiated a DNS lookup: Android's system resolver may own the socket, and lookup may fail. A hostname match alone does not identify an app. Static APK findings indicate possible capability or embedded indicators, not runtime execution. The launcher-visible permission audit reports manifest declarations and current grant flags only; package visibility means it is not a complete system/OEM inventory.
- **No dynamic APK analysis.** APK signature integrity is now verified by the Android adapter using `apksig`, but the audit still does not install or execute the APK, establish permission grants, inspect every code path, or prove that a capability was used. The Rust CLI's v2/v3 certificate extraction remains metadata-only and is not a signature verifier.
- **No generic permission shim on stock devices.** An ordinary Android app cannot freely revoke every other app's permissions or intercept every sensor/API call. iOS cannot inspect other apps' binaries or override their permissions outside approved system APIs and entitlements.
- **No claim of encrypted local preferences.** PCAGE export encryption does not imply that all on-device settings, logs, caches, or crash artifacts are encrypted at rest. Signed audit checkpoint files are plaintext JSON; a signature does not provide confidentiality.
- **No claim that an imported signature is unquestionably malicious.** Active records are sourced indicators with known service semantics; broad/shared endpoints remain review-only where blocking could break unrelated functionality.
- **Metadata removal is format-bounded.** The Rust core supports JPEG, PNG, and WebP. It removes recognized metadata chunks/segments and verifies a second parse of the saved candidate. Other JPEG APP markers, unknown PNG/WebP extensions, and ICC color profiles are preserved and may carry metadata. The parsers validate container boundaries (and PNG CRCs) but do not decode pixels, prove every decoder will render the output, or anonymize details visible in the image itself.
- **No legal request automation yet.** The legal request assistant is planned, not established as implemented by this branch. Even after it is built, a submitted request will not prove that a company or downstream recipient erased the data.

## Required checks

Run from the repository root:

```sh
go -C shared/go/pcage-tools test ./...
go -C shared/go/pcage-tools run . validate-tracker --max-age-days 180
go -C shared/go/pcage-tools run . tracker-report --format markdown
go -C shared/go/pcage-tools run . validate-android-backup
go -C shared/go/pcage-tools run . validate-android-privacy
cargo fmt --manifest-path shared/rust/pcage-audit/Cargo.toml --all -- --check
cargo test --manifest-path shared/rust/pcage-audit/Cargo.toml
cargo clippy --manifest-path shared/rust/pcage-audit/Cargo.toml --all-targets -- -D warnings
cargo fmt --manifest-path shared/rust/pcage-crypto/Cargo.toml --all -- --check
cargo test --manifest-path shared/rust/pcage-crypto/Cargo.toml
cargo clippy --manifest-path shared/rust/pcage-crypto/Cargo.toml --all-targets -- -D warnings
```

A green static check is evidence only for the invariant it tests. It does not replace Android emulator/device tests, iOS entitlement approval, independent cryptographic review, or a real interoperability test across every shipping implementation.

## Security change gate

1. New tracker signatures require evidence that supports the exact indicator and a human review of collateral blocking risk.
2. New profile format versions require a new explicit version/magic, updated format documentation, and shared interoperability vectors. Never change KDF parameters silently.
3. Any future remote catalog updater must use an established update framework such as TUF for authenticated, versioned, expiring metadata and rollback/freeze protection; HTTPS and a schema-valid JSON file alone are insufficient.
4. Any future sync protocol must establish peer/device identity, key lifecycle and revocation, replay/conflict handling, recovery semantics, and metadata exposure before claiming end-to-end encryption.
5. Any new diagnostic must report failed or unobservable paths explicitly. A missing observation is not evidence that no tracking occurred.
